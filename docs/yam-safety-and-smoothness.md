# YAM 実装の分析：安全ガードと方策出力の滑らかな送信

作成日：2026-10-22．対象：`/home/tetsugo_local/workspace/YAM`（HEAD `839fb55`）．状態：調査メモ．roboloom への取り込み方針は §5 と [次期設計](../dora-lerobot-next-design.md) の §11 にまとめる．

YAM は双腕 YAM アーム（DM4340/4310 モーター，CAN）で，テレオペ，データ収集，MolmoAct-v2 の評価を行う実装である．本文の行番号は上記 HEAD のもので，パスは `gello_software/` を `gs/`，`i2rt/i2rt/` を `i2/` と略す．コードは読んだだけで，実機での挙動は確かめていない．数値は特記がない限り実運用の設定 `gs/configs/yam_left.yaml` の値である．

roboloom は複数の機体に対応する．このため YAM の工夫を次の三つに分けて読む．

- **汎用**：どの機体でも同じ形で使える考え方．roboloom の共通部分に入れる．
- **機体能力**：特定のハードウェアの機能に依存する．roboloom では機体ごとに申告させ，起動時に確かめる．
- **運用上の対処**：YAM の単一プロセス構成のために必要になったもの．roboloom の構成で不要になるか，形を変えて残るかを分けて考える．

## 1．構成とレート階層

| 層 | 周期 | 実体 |
| --- | --- | --- |
| カメラ | 30 fps，640×360 color | 別プロセスの camera server（ZMQ REP/PUB） |
| 方策推論 | 1 回約 0.86 s（実機），背景スレッドでほぼ連続 | `gs/gello/rtc/engine.py` の `RTCInference` |
| 方策ステップ | 10 Hz（学習データは 30 Hz） | `ActionQueue` から 1 action を取り出す |
| チャンク長 H | 30 actions | MolmoAct2 の flow-matching head |
| 制御ループ | 10 Hz × 補間倍率 3 = 30 Hz | メインスレッド，絶対デッドライン |
| i2rt サーバースレッド | 約 200 Hz（`update()` の後に 4 ms の sleep） | `i2/robots/motor_chain_robot.py:261-289` |
| CAN 送信 | 250 Hz | `i2/motor_drivers/dm_driver.py:492-547` |
| モーター | オンボード PD（MIT モード）．kp=[80,80,80,40,10,10]，kd=[5,5,5,1.5,1.5,1.5] | DM4340／DM4310 |

```text
RealSense ×3 ─► camera_server（別プロセス）
                    │ 要求時だけ取得（timeout 500 ms，0.5 s より古いフレームは拒否）
メインスレッド 30 Hz ───────────────────────────────────────────────
  3 tick に 1 回：obs を取得 → engine.notify_observation（s_obs を記録）
                  → queue から 1 action → 補間器へ
  毎 tick：補間値 → apply_safety（NaN，グリッパー clip，±0.03 rad/tick）
          → floor guard → YAMRobot.command_joint_state
          （queue が空なら何も送らず，ドライバが最後の目標を保持）
RTCInference スレッド ───────────────────────────────────────────────
  queue 残り ≤ 22 なら：前チャンクの s_obs 以降を prefix にして RTC 誘導付きで推論
                        → merge(chunk, start_step=s_obs)
i2rt：目標をラッチ → 重力補償トルク ×1.3 とグリッパー力制限を加える → 250 Hz CAN → モーター PD
```

## 2．安全ガード

### 2.1 層ごとの仕組み

### 2.2 設計の要点

1. **故障の種類ごとに止め方を変えている．** ファームウェアとドライバの異常では脱力する．床面に近づいたら切り詰めるか保持する．カメラ障害では保持して一時停止する．方策の異常では保持し，その後 park する．「何が壊れたら，どの状態に移るか」を障害ごとに決めている．
2. **最終の clamp の基準を，最後に送った指令にしている．** 実測ではなく送信値を基準にするので，PD の追従遅れで clamp が連続することがない．clamp した tick には印を付けて記録し，その割合を後で評価する．
3. **重い処理は通電中にしない．** モデルのロード，GC，RealSense の再起動，データセット変換はどれも GIL を数百 ms 以上握る．これが 250 Hz のスレッドを止め，400 ms のウォッチドッグで両腕が落ちるという事故が実際に起きていた．YAM の対処は二つある．処理を通電の前か解放の後に寄せることと，`gc.freeze()` である．
4. **人が関わる関門を置いている．** leader が離れていれば開始しない．解放前に確認を取る．ガードの無効化には明示的なフラグが要る．設定の確認には `start_joints_confirmed: true` のような申告を要求する．
5. **障害を前提に，片付けの順序を組んでいる．** 腕は組み立て直後に登録するので，2 本目の構築に失敗しても 1 本目を解放できる．推論スレッドを先に止めてから park する．

### 2.3 弱点（コードから読み取れるもの．実機では未確認）

- ウォッチドッグのレジスタを実行時に読み戻していない．0（無効）のままのモーターがあると，「指令を止めれば脱力する」という前提が黙って崩れる．終了時に motor-off フレームも送らない．
- ドライバのスレッドが死んでも，収集以外の起動スクリプトは気づかない．キャッシュされた状態を読み，死んだバッファに書き込み続ける．
- 応答しないモーターがあると，再試行のため CAN スレッドが最大で約 3 s 止まる．ウォッチドッグより長いので，同じバスの他のモーターも落ちる．
- `clip_motor_torque` の既定値が `inf` で，トルク上限が実質的に効いていない．温度は表示するだけで，出力を下げたり止めたりしない．
- 起動直後は zero-gravity モード（kp=0）で，重力補償は 1.3 倍の過補償になっている．最初の位置指令までの間に腕が浮いたり流れたりしうる．
- floor guard は MolmoAct の評価スクリプトでしか使っていない．収集，テレオペ，再生では効いていない．
- 同期評価の HTTP 推論 `requests.post` にタイムアウトがない（`gs/experiments/molmoact.py:210`）．
- ポートが使用中のとき，`fuser -k` で使用中のプロセスを殺す（`gs/gello/dynamixel/driver.py`）．別の収集プロセスを殺すと，その腕が落ちる．
- 記録つき RTC 評価で `saver.add_step` に必須引数の `action` を渡していない（`gs/experiments/launch_yaml_eval_molmoact_rtc.py:441`，`gs/gello/utils/eval_utils.py:98-104`）．2 回目の方策 tick で `TypeError` になるはずである．テストの代役オブジェクトは引数 2 個なので検出していない．ループ版は記録しないので影響しない．

## 3．方策出力を滑らかに送る工夫

### 3.1 非同期推論と置換式の ActionQueue

同期式では，推論している 0.6〜0.9 s の間アームが止まり，チャンクの境目ごとに停止する．YAM の RTC 経路では，推論を背景スレッドで回し，制御ループは前のチャンクを実行し続ける．

- queue の残りが `queue_threshold=22` 以下になったら次の推論を始める．merge の直後で残りが約 20 なので，推論はほぼ連続して回る．
- ActionQueue は**置換式**である．新しいチャンクが来たら，前のチャンクの残りは捨てる．
- **step clock**：queue は取り出した回数 `_steps` を数える．観測を通知した時点の回数を `s_obs` として記録し，merge では `_steps − s_obs` 個を正確に捨てる（`gs/gello/rtc/action_queue.py:141-156`，`:221-228`）．経過時間からではなく，**実際に消費した数**から捨てる量を決める．
- この時刻合わせの修正（`1475441`）の前は，prefix が 1 ステップずれていた．計画が 1 action 後戻りして止まって見える症状が出ていた．実測では，継ぎ目の段差が 0.111 → 0.022 rad，clamp された tick が 10% → 3% に減った．
- **エポック**：`reset()` で queue を空にしてエポックを進める．リセットより前に始まった推論の結果は，merge の時点で捨てる（`engine.py:238-244`，`:419-431`）．
- 指示文を変えても queue は空にしない．空にすると推論 1 回分止まるので，次のチャンクから効かせる．

### 3.2 遅延の推定

- 遅延は観測の通知から merge までを測る．`d = ceil(L × fps)` で，単位は方策ステップである．
- 誘導に使う d は，直近 100 回の**最大値**から求め，`execution_horizon` を上限にする．最初の 1 回（コールドスタート）は除く．
- 実測では，実際に消費した d が約 9.5 であるのに対し，推定は約 13.6 で過大だった．p95 にする案が文書で検討されているが，実施していない．
- 起動時に，設定が方策の出力と矛盾しないかを検査する（`launch_yaml_eval_molmoact_rtc.py:124-172`）．`eh > H`，`q ≥ H`，`d ≥ H` はエラー，`q < d`（queue が枯れる），`d > eh`（重みが 1 から 0 に段差で落ちる），`q < eh` は警告である．

### 3.3 RTC 誘導（チャンク間の inpainting）

- prefix は，前チャンクのうち s_obs 以降の**正規化された**行である．長さが足りない分は末尾の action を繰り返して埋める．0 で埋めると，正規化空間では「データセットの平均」を意味してしまうからである．
- 正規化が上下限つきの方式なら，prefix を [−1,1] に clip する．逆正規化で clip されたものが実際に実行された値だからである．
- 重み：`i < d` なら 1，`d ≤ i < eh` なら線形に 1 から 0 へ下げ，`i ≥ eh` なら 0（`guidance.py:99-127`）．
- 誘導つき速度は閉じた式で計算する：`x̂₁ = x_t + (1−t)v`，`v' = v + gw(t)·(prev − x̂₁)⊙w`．VJP を使わないので，autograd の追加コストがない．
- ゲイン `gw` は τ に対して U 字型で，上限 `β = min(max_guidance_weight, num_steps)` で抑える．1 ステップの補正が 1 を超えると Euler 更新が目標を飛び越えるためである．
- 調整の経緯：
  - β を 10 から 5 に下げた．実行された action の 48% が w=1，つまり前の計画をそのまま写したものだったからである．
  - eh を 14 から 20 に上げた．d が eh に張り付くと，重みが 0 と 1 の中間になる区間がなくなり，境目に段差が出たからである．代わりに反応性が下がる．
- CUDA graph は無効にする．graph を再生すると，flow loop の差し替えを素通りしてしまう．
- 最初のチャンクは prefix なしで生成する．

### 3.4 送信レートへの補間

- `ActionInterpolator` は，方策の action 1 個から `prev + (i/N)(a − prev)` を N−1 個，最後に `a` そのものを出す．N=3 である（`gs/gello/rtc/interpolator.py`）．
- `prev` は merge をまたいでも持ち越す．このため継ぎ目の段差も N tick に分散する．
- ドライバ側には補間も速度フィードフォワードもない．約 33 ms のゼロ次ホールドを，モーター内の PD が滑らかにしている．速度に比例した追従遅れがあり，指令は実測より平均 0.04〜0.11 rad 先行していた．

### 3.5 固定周期ループと停止の扱い

- 絶対デッドライン方式で，次の期限を `deadline += period` で決める．1 周期を超えて遅れたら `deadline = now` に戻し，取り返そうとして連続送信しない．
- **queue が空になったら何も送らない．** ドライバが最後の目標を保持するので，アームはその場で止まる．空になった tick と，最初の action を待つ tick は分けて数える．
- 世代 2 の GC が約 4 s ごとに約 106 ms 止まっていた．overrun はすべてこれが原因で，CAN スレッドも一緒に止まっていた．対処として，通電の前に `gc.collect(); gc.freeze()` を行う．GC の発生は記録に残す．
- 方策の入力にする状態は `observation_source: command` で，最後の指令を使う．学習データが指令値を状態として記録していたからで，measured にすると精度が落ちた（`d946833`）．
- 開始時：開始姿勢を保持したまま最初のチャンクを待つ（約 1 s）．最初の action は補間せず，clamp だけで出す．ループ版は，**実測の**関節が開始姿勢の 0.05 rad 以内に入ってから次の指示を受け付ける．
- 終了時：減速の区間はない．最後の指令で止まる．

### 3.6 滑らかさの測り方

`rtc_trace.npz` と `gs/experiments/rtc_trace_report.py` は次を出す．滑らかさを主観でなく数値で議論するための道具で，roboloom の測定項目にも使える．

- tick 周期の分布，overrun と GC の重なり，overrun の間隔の変動係数（周期的なら GC を疑う）．
- 追従誤差 `|measured − sent|`，速度のピーク．
- **進み比** `(v_i·v_{i−1})/|v_{i−1}|²`．+1 は等速，負は計画の後戻りを表す．
- 継ぎ目と index ごとの段差，clamp の回数，queue が空になった回数．
- 実行された action の重みの内訳（w=1，中間，w=0）．d が eh に張り付いた割合．

`rtc_offline_check.py` はロボットなしで，2 つの観測から作ったチャンクの prefix の一致度と継ぎ目の段差を測る．

### 3.7 同期経路との比較

同期評価の `dynamic_smoothing` は，1 action を `max(腕Δ/0.1, グリッパーΔ/0.02)` 個（上限 100）の直線サブステップに分け，30 Hz で送る．速度は実質的に閾値で抑えられ，推論中は静止する．RTC は止まらないが，追従遅れが大きく，それが精度低下の一因と見られている．

## 4．分類の要約

| 工夫 | 汎用か | 備考 |
| --- | --- | --- |
| step clock と s_obs による時刻合わせ，置換式 queue，エポック | 汎用 | チャンクを出す方策なら全般に使える |
| RTC 誘導 | 方策の能力 | flow-matching や拡散の推論ループに手を入れられる方策に限る |
| 補間（prev を持ち越す） | 汎用 | 送信レートは機体で異なる |
| 最後に送った値を基準にした変化量の clamp と記録 | 汎用 | 上限は rad/s などの物理量で持つ |
| queue が空なら保持 | 汎用（保持の手段は機体能力） | 位置制御の機体なら最後の目標を保持できる．速度制御では 0 速度を送る |
| 起動前の互換性検査，重い処理を通電前に寄せる | 汎用 | |
| park → 確認 → release | 汎用（release の手段は機体能力） | YAM はウォッチドッグ任せ．Dynamixel はトルクオフを明示的に送る必要がある |
| 障害ごとの遷移（脱力，保持，一時停止） | 汎用（どれを選べるかは機体能力） | ブレーキのない重い腕で脱力を選ぶと落下する |
| floor guard（運動学的な経路検査） | 汎用の枠組み，機体モデルが必要 | モデルがない機体では使えない |
| 通信ウォッチドッグ，ファームのエラーコード，MIT モードの PD，kp/kd，重力補償，グリッパー力制限 | 機体能力 | DM モーター固有のもの |
| leader の PWM 駆動による姿勢合わせ | 機体能力 | Dynamixel の leader 固有 |
| GC の固定，カメラの別プロセス化，通電中の重い処理の回避 | 運用上の対処 | dora-rs のノード分割に置き換える（§5.6）．robot ノード内の GC と資源の競合は残る |

## 5．roboloom への取り込み方針

### 5.1 機体能力の申告

`Robot` に，機体が持つ機能を宣言する仕組み（`capabilities`）を加える．robot ノードは起動時にこれを読み，安全上必要な能力がなければ起動を拒否するか，明示した代わりの動作を選ぶ．能力が「あるはず」として扱う箇所を作らない．

| 能力 | 例 | 使う箇所 |
| --- | --- | --- |
| `hardware_watchdog_ms` | YAM：400 ms，Dynamixel：なし | 起動時にレジスタを読み戻して照合する．なければ robot ノードが明示的に脱力するか保持する |
| `release` | トルクオフ指令，ウォッチドッグ任せ，ブレーキ | park → release の手段 |
| `safe_stop` | `hold`，`limp`，`brake` | 障害時の遷移先．重力で落ちる機体では `limp` を選べなくする |
| `fault_codes` | DM のエラーコード，Dynamixel の Hardware Error Status | 毎周期検査して FAULT をラッチする |
| `effort` / `temperature` | 電流，トルク推定，温度 | グリッパー詰まりの制限，温度での出力低下や停止 |
| `onboard_pd` / `velocity_feedforward` | MIT モード，xArm の servo モード | 補間器が出す速度を送るかどうか |
| `kinematic_model` | URDF や MJCF | floor guard，作業空間の制限 |

既存の Rakuda の Dynamixel 実装では，ウォッチドッグがない前提で HOLD と停止の意味を決める．YAM の「止めれば脱力する」をそのまま移さない．

### 5.2 安全判定（`FollowerSafety`）の改修候補

現行の `FollowerSafety.tick` は，範囲外や `max_step` 超過の指令を**拒否して HOLD** にする．leader 操作なら妥当だが，方策の出力ではチャンクの継ぎ目の小さな段差でも停止し，ガクつきの原因になる．YAM の運用をふまえ，二段階に分ける．

1. **soft clamp**：最後に送った値から，`max_speed`（rad/s やカウント/s）× 実際の tick 間隔までに切り詰めて送る．`clamped` の印と，希望値・送信値の両方を記録する．
2. **hard reject**：NaN，次元違い，期限切れ，関節範囲外，明らかに大きな飛び（soft の上限の数倍）．これまで通り HOLD にし，必要なら FAULT をラッチする．

上限は tick あたりの値ではなく物理量で持つ．制御周期を変えても意味が変わらないようにするためである．

### 5.3 方策用の経路

方策の出力は `ActionChunk` として扱い，[次期設計](../dora-lerobot-next-design.md) §4 の案を具体化する．

- `policy-*` ノードがチャンクを出し，`controller-policy` が queue，step clock，補間を持つ．YAM の `s_obs`，`start_step`，エポックの考え方をそのまま使う．時刻は経過時間でなく消費数で揃える．
- RTC 誘導は方策の能力として扱う．推論ループに手を入れられない方策では，誘導なしの置換式 queue と補間だけを使う．
- 補間の結果を毎 tick dora で送るか，時刻つきの短い経由点列を robot ノードに渡して robot ノードが補間するかは，dora 越しのジッタを測って決める．後者なら IPC の揺れが送信周期に響かないが，robot ノードの責務が増える．
- queue が空になったら何も送らず，robot ノードが期限切れとして保持する．空になった tick を数えて記録する．
- 推論の失敗，形状の不正，NaN はチャンクの段階で拒否する．続いたら session に停止を求める．

### 5.4 セッションと記録

- 通電の前に，方策ノードのロードとウォームアップ，方策出力と設定の互換性検査を済ませる．session は，方策ノードの準備完了を受け取ってから robot ノードに通電を指示する（§5.6）．
- 終了は park → 確認 → release の順にし，release の手段は機体能力から選ぶ．
- `observation.state` には実測と最後の指令の両方を保存する．方策にどちらを入力するかは設定で選び，メタデータに残す．YAM では，学習時と評価時でこの意味が食い違ったことが精度に効いた．
- recorder の測定項目に，YAM の trace にある指標を加える：tick 周期，clamp の割合，queue が空になった割合，継ぎ目の段差，進み比，追従誤差．

### 5.6 GIL と GC への対処を dora-rs の構成に置き換える

YAM は推論，カメラの一部，記録，CAN の送信スレッドを同じ Python プロセスに置いている．このため，GIL を長く握る処理が 250 Hz のスレッドを止め，ウォッチドッグで腕が落ちた．YAM の対処は，処理の時期をずらすこと（通電前，解放後），`gc.freeze()`，カメラの別プロセス化である．

roboloom では，[次期設計](../dora-lerobot-next-design.md) §3 の方針どおり，dora-rs のノードとしてプロセスを分ける．Python ノードはそれぞれ別のインタプリタで動くので，GIL はノードごとに独立する．YAM の各問題を次のように置き換える．

| YAM の問題と対処 | roboloom（dora-rs）での扱い | 残るもの・確かめること |
| --- | --- | --- |
| モデルのロードと推論が GIL を握り，CAN スレッドを止める．通電前にロードする | `policy-*` ノードを別プロセスにする．robot ノードの GIL には影響しない | GPU と CPU の競合．通電の前に方策ノードが準備完了を返す手順は残す（起動直後の推論の遅れで queue が枯れないようにするため） |
| RealSense の再起動が GIL を握る．カメラを別プロセスの server にする | `sensor-*` ノードとして最初から分ける．再起動や USB リセットもそのノード内で行う | USB 帯域の共有．リセット中は欠損として記録する |
| データセット変換と PNG 保存が GIL を握る．解放後に変換し，保存スレッドを nice 10 にする | recorder ノードを別プロセスにする．変換はセッション後か別ジョブにする | ディスクと CPU の競合．収録中の制御周期への影響を測る（TODO 段階 3） |
| 世代 2 の GC が約 4 s ごとに約 106 ms 止まる．`gc.freeze()` で抑える | robot ノード内の問題として残る．robot ノードは毎周期の割り当てを減らし，起動後に `gc.freeze()` するか，世代の閾値を調整する．GC の発生を記録する | robot ノードの tick 周期の p99 と最大で効果を確かめる |
| CAN 送信を Python スレッドで回す | robot ノードの中に閉じる．ウォッチドッグを持つ機体では，robot ノードが止まっても機体側で脱力する．持たない機体では，robot ノードの停止が保持のままになる | 機体能力 `hardware_watchdog_ms` で分ける（§5.1）．robot ノードの周期を timer で駆動するかノード内で待つかは実測で決める |
| 30 Hz の指令をメインスレッドから直接ドライバに渡す | controller から robot ノードへ dora のメッセージで渡す．robot ノードは最新の有効な指令だけを使う | dora 越しの遅延とジッタ．入力の `queue_size` を 1 にして古い指令を溜めない．経由点列を送る案（§5.3）の判断材料にする |
| 方策スレッドの例外を `shutdown_event` で制御ループに伝える | 方策ノードは異常を session に送る．robot ノードは指令が期限切れになれば単独で保持に移る | ノードが死んだときの検出．dora の自動再起動は使わない（次期設計 §5） |
| 画像を 2 MB の pickle で同期 REQ する | 画像は dora のメッセージ（Arrow，共有メモリ）で方策ノードに直接送る．robot ノードは画像を受け取らない | 方策ノードでの画像の鮮度（取得時刻）を記録する |

dora でプロセスを分けても，CPU，GPU，USB，メモリ，ディスクは共有される．「別プロセスだから周期が乱れない」とはみなさず，YAM で効いた項目（GC，推論中，カメラ復旧中，記録中）ごとに robot ノードの tick 周期を測る．

### 5.7 取り込まないもの

- `fuser -k` や `sudo chmod` による機器の奪取．使用中なら起動を拒否する．
- タイムアウトのない推論呼び出し．
- トルク上限 `inf` を既定値にすること．
- YAM の数値（0.03 rad/tick，kp/kd，重力補償 1.3 倍，50 N など）．機体ごとに実測して決める．

## 6．実装時の設計上の注意

1. 機能は「汎用の契約」と「機体能力」に分けて実装する．robot ノード，controller，方策ノードの共通部分に，特定のモーターのレジスタ，フレーム形式，ゲインを書かない．
2. 能力に依存する安全機能は，起動時に申告と実機の値（読み戻し）の両方で確かめる．ない場合の動作を明示的に選び，黙って弱めない．
3. 上限と期限は物理量と時間で持ち，tick あたりの値は実際の周期から計算する．
4. 安全判定の結果（clamp，reject，HOLD，FAULT）はすべて記録に残し，滑らかさと安全を数値で評価できるようにする．
5. 障害ごとに遷移先を決め，機体の機構（重力負荷，ブレーキの有無）で選べる遷移を制限する．
6. 新しい機体を追加するときは，能力の表を埋め，§5.1 の照合と異常注入の試験を通してから実機で動かす．
